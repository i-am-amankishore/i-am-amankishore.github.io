Essay

Why agents need evals

Aman Kishore, Head of Product at TruKKer

Most AI agent demos are lies of omission. They show you the run that worked. The founder types a question, the agent answers beautifully, the room nods. What the demo never shows is the other forty runs, the ones where the agent confidently did the wrong thing to someone who was not in the room to catch it. In a demo, a wrong answer is a laugh. In production, a wrong answer is a customer.

The gap between those two worlds is not a better model. It is an eval.

An eval is a fixed set of labeled cases and a script that measures how the agent does against them. It sounds like testing because it is, but the mindset is different. A unit test asks "did this function return 4." An eval asks "of the hundred messages a customer might send, how many did we handle correctly, and of the ones we got wrong, how badly." That second clause is where the product judgment lives.

The number that decides whether you ship

I build agents for a freight marketplace, so let me use one. An inbound triage agent reads a message, decides what it is about, and either answers it or routes it to a human. Accuracy sounds like the metric that matters. It is not. The metric that matters is what happens on the misses.

Consider two agents that are both 92% accurate. The first one, when it is wrong, sends a slightly off but harmless reply. The second one, when it is wrong, auto-answers a furious customer who asked about a missing payment. Same accuracy, completely different products. One is shippable. The other will lose you an account by Friday.

Overall accuracy is the number people quote. Escalation recall is the number that decides whether you ship.

So the eval I actually gate on is not accuracy. It is escalation recall: of the messages that must reach a human, complaints and payment disputes, how many did. That number has to be 1.00. Not 0.98. If the agent auto-answers even one angry customer about their money, the release does not go out, and the eval script says so in plain words: DO NOT SHIP.

Evals turn opinions into decisions

Before I had an eval, every argument about the agent was a matter of taste. Someone felt it was too aggressive. Someone else felt it was too timid. We would tune a prompt, watch a few examples, and convince ourselves. It was theater with a keyboard.

The first time I ran a real eval on that triage agent, it scored 0.90 on escalation recall, and the reason was specific: one invoice dispute had been classified as a routine status check and auto-answered. I had not noticed in casual testing because the wording looked calm. The eval noticed. The fix was a guardrail that routes anything mentioning money to a human even when the classifier is confident it is routine. Policy beat classification, and I only knew to write that policy because a labeled case caught the exact failure. The eval paid for itself on its first run.

That is the real value. An eval converts vibes into a decision you can defend. It lets you say "we do not ship below 1.00 escalation recall" and have that mean something, the same way a company that says it cares about quality but ships anyway does not actually care about quality. The commitment is only real if something can fail it.

What this means if you lead product

You do not need to write the eval yourself, but you do need to insist it exists, and you need to be the one who decides what the gate is. That decision is not technical. Choosing that escalation recall must be perfect while accuracy can sit at 0.92 is a statement about which mistakes your business can survive and which it cannot. That is product strategy wearing a lab coat, and handing it to whoever happens to be tuning the prompt is how you end up with an agent optimized for the demo instead of the customer.

The uncomfortable part is that a good eval will slow you down. It will block releases you wanted to ship and force conversations you wanted to skip. That friction is the feature. An agent with no eval is not faster, it is just failing where you cannot see it yet. The teams that win with AI are not the ones with the best model. They are the ones willing to write down, in a file that can go red, what wrong is not allowed to look like.
